# Design

*2026-07-20*

I've been thinking about rewriting my blog system for a while. Today, GitHub
Actions took two hours to deploy a simple change because it couldn't find a
free runner. I'm taking this as a sign that it's time to start running my own
blog server.

This article is for me to organise my thoughts on what I want, and what I
should build first.

## Roadmap

1. Terminal-native

   Some kind of terminal interface to this system is non-negotiable.

1. Template language

   Translate my blog's current contents into a type-safe template language and
   check that everything works.

1. File storage

   If I'm going to use a relational database for this, then it has be queryable
   using Datalog. I'm not going to build another personal system on top of SQL
   if I can avoid it. But that's a decent little research effort.

   In the meantime, I'll just use the file system for my database. It has no
   referential integrity, but I think that's a reasonable tradeoff at my scale.

1. Incremental updates

   Define the site's build system.

1. Mass import / restore

   I don't want to manually copy each blog resource. So I should just automate
   the process by:

   1. Defining my backup format
   1. Translating my current blog into that format
   1. Restoring all that content into an empty deployment

   Questions:

   * How should a batch restore handle failure for a subset of resources? 

1. Music hosting

1. Backups

1. Versioning

1. Live configuration

   Until this point, the system behaviour (e.g. site layout, template
   dependencies) has been defined in code that needs to be recompiled and
   redeployed.

   Now the system configuration becomes first-class; just another resource.
   It's edited and versioned the same way as articles are, and maybe even
   defines the incremental rebuild behaviour for itself.

## Unfiltered feature list

* Decent template language for writing web pages, articles, etc.

* Articles can be tagged, browsed by tag.

* Incremental updates

  Changing a resource on the server only rebuilds downstream dependencies.

* Draft mode

  The authoring process involves writing a (privately-viewable) draft and then
  "publishing" it when I'm happy.

* Resource versioning

  e.g. change history for articles

* Terminal-native

  I shouldn't have to open a web browser to administer this system.

* Music hosting

  SoundCloud is anal about copyright infringement. I might not be able to get
  covers published there. I should be able to take the *POSSE* approach with
  my music.

* Comments

  A while ago I removed Disqus, which hosted my comments. I'd like to bring the
  comment section back.

* Manual comment approval

  I think for the time being, comments should only be made public after I've
  approved them. I might also have a moderation log to show comments I haven't
  approved. Depends on how much spam there is.

* Email notifications for comments

  I should get an email telling me about a new comment. Then I could just click
  an "approve" or "reject" button in the email to respond.

* Analytics

  Track things like the `Referer` HTTP header to get a sense of my site's
  traffic. Would be nice if I could get a sense of feed usage, too.

  No client fingerprinting.

* Feeds

  RSS/Atom feed, at the very least for the blog articles. But you could have
  feeds for so many of these other features, which I think would be cool even
  if no one uses them.

* Webmentions?

* File and media storage

  e.g. slides for talks, images embedded in posts

* Server-side math typesetting and syntax highlighting

* Sitemap for web crawlers

* Backups

  I'm thinking of taking an "image-based" approach, with a local editing support.
  So the server is the source of truth for these resources, but working on
  something from the terminal can tolerate disconnects. If I save the file but
  the internet is unavailable, I still have my local copy which can be uploaded
  later.

  Since the server will be the source of truth, I need to be able to back it up
  in case it loses data.

* Live configuration

  I should be able to change the behaviour of the system in the same way that
  I change the content. Recompile and redeploy should be extremely rare.
